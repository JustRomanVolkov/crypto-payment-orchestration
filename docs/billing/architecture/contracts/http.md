# HTTP-контракт Billing

[Billing](../../README.md) → [Архитектура](../README.md) → Контракты

Ниже показан маршрут при размещении Billing под `/api/v1/billing`; общий префикс согласуется с API платформы. Клиенту доступны создание и чтение Payment. Webhook — отдельный вход PSP. Клиент не выбирает PSP и не запускает переключение.

| Метод и путь | Кто вызывает | Результат |
|---|---|---|
| `POST /api/v1/billing/payments` | Авторизованный покупатель | Создание одной логической оплаты покупки или результат допустимого повтора. |
| `GET /api/v1/billing/payments/{payment_id}` | Авторизованный владелец | Сохранённый статус и действие для покупателя, без запроса к PSP. |
| `POST /api/v1/billing/webhooks/{endpoint_id}` | PSP | Подтверждение долговременного приёма проверенного сообщения. |

## Создать Payment

Тело запроса содержит `purchase_id` и выбранные покупателем `asset` и `network` из разрешённых вариантов; заголовок `Idempotency-Key` обязателен. Tenant и владелец устанавливаются из доверенной авторизации. Цена и предмет поступают из доверенного снимка покупки, маршрут и адрес выплаты платформе — из серверной конфигурации. Адрес, по которому покупатель отправит перевод, выдаёт PSP после создания счёта; клиент его не задаёт. Отпечаток намерения включает покупку и выбор актива/сети, но не текущую цену каталога.

Первый commit возвращает `202 Accepted` с `payment_id`, `status=PROCESSING` и `status_url`: работа по созданию счёта уже сохранена, реквизиты могут появиться позже. Повтор того же намерения с тем же ключом возвращает этот Payment с его **текущим** сохранённым состоянием (`200 OK`), даже если цена в каталоге изменилась. Изменённое намерение с тем же ключом и новый ключ на уже занятую покупку дают `409 Conflict`. Уникальность и гонки определены в [правилах согласованности](../consistency.md).

Тело ошибки содержит машинный `code`. Неподходящий актив или сеть в запросе покупателя дают `422` с `code=PAYMENT_OPTION_UNSUPPORTED`: выбранный способ не подходит для этой покупки. Если запрос допустим, но нет ни одного подключённого PSP с подходящим merchant account, ответ — `503` с `code=PAYMENT_METHOD_UNAVAILABLE`: счёт не инициирован, выбранный способ сейчас недоступен. Временная невозможность подтвердить сохранение — отдельный `503` с `code=PAYMENT_STATE_UNAVAILABLE`: исход команды может быть неизвестен, поэтому клиент повторяет запрос с тем же ключом, а не начинает новый платёж. Потеря ответа также не доказывает rollback.

Один `purchase_id` остаётся закреплён за одним Payment даже после `FAILED` или `EXPIRED`: новый ключ для него возвращает `409`. После `FAILED` без созданного счёта модуль продукта может разрешить новое намерение с новым `purchase_id`; клиент использует для него новый `Idempotency-Key`. После `EXPIRED` с выданными реквизитами клиенту нельзя автоматически предлагать новую оплату: старый счёт ещё может получить деньги. Новое намерение допустимо лишь после сверки и решения модуля продукта; связь двух покупок и обработка позднего поступления описаны в [денежных исключениях](../flows/exceptions.md).

## Получить состояние

Ответ содержит `payment_id`, статус Payment, `review_required` и действие `PAY`, `WAIT`, `CONTACT_SUPPORT` или `NONE`. `PAY` допустим только при проверенных пригодных реквизитах и отсутствии ожидающего денежного свидетельства. Тогда возвращаются данные одной Attempt: PSP, точная сумма строкой, актив, сеть, платёжный адрес покупателю от PSP и применимый дополнительный идентификатор либо размещённая ссылка. Истёкшие или непроверенные реквизиты не сопровождаются приглашением платить. При `PAID` действие `NONE` означает, что оплата принята и повторно платить не надо; оно не подтверждает, что доступ уже открыт. Состояние предоставления покупки клиент получает из API модуля продукта. Если интерфейсу нужен единый ответ, его составляет отдельный объединяющий API платформы; этот контракт Billing такого ответа не задаёт.

Доступ проверяется по tenant и владельцу покупки; чужой или отсутствующий ID возвращает `404`. Чтение локально и не инициирует create, GET к PSP или выдачу.

## Принять webhook

`endpoint_id` соответствует зарегистрированным PSP, merchant account, среде и набору секретов для проверки подписи; сам идентификатор не является секретом. Verifier проверяет исходные байты, заголовки и правила конкретного PSP. Подлинное сообщение сохраняется даже при пока неизвестной привязке к Payment. Точный повтор принимается без повторного денежного эффекта; противоречащее сообщение не затирает исходный факт.

`2xx` означает успешный commit наблюдения, а не подтверждённую оплату или выдачу. Неверная подпись даёт `401/403`, некорректный формат — `400`, неудавшееся сохранение — `5xx`, чтобы PSP мог повторить доставку. Денежное решение выполняется отдельно по [правилам подтверждения](../flows/settlement.md).
