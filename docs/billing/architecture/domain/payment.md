# Агрегат Payment

[Billing](../../README.md) → [Архитектура](../README.md) → Домен

Payment представляет одну логическую оплату покупки. Его агрегат задаёт границу согласованности: изменение попыток и решение об оплате проходят через корень `PaymentAggregate`. Смена PSP создаёт следующую попытку внутри того же Payment, сохраняя покупателя, предмет и согласованную цену. [Состояния](states.md) описаны отдельно.

## Состав агрегата

| Объект | Роль | Что хранит или решает |
|---|---|---|
| `PaymentAggregate` | Aggregate Root | Идентификатор и снимок покупки, маршрут, попытки, решение об оплате. Разрешает новую попытку только при соблюдении инвариантов всего Payment. |
| `PaymentAttemptEntity` | Дочерняя Entity | Одну логическую операцию с выбранным PSP: подготовку, исход создания счёта, реквизиты и наблюдаемое состояние оплаты. |
| `MoneyValueObject` | Value Object | Точную сумму и валюту; цена покупки и криптовалютная сумма к переводу не взаимозаменяемы. |
| `CryptoAssetValueObject` | Value Object | Актив вместе с сетью и, когда применимо, идентификатором токена. Одного тикера для проверки перевода недостаточно. |
| `RouteSnapshotValueObject` | Value Object | Применённую версию политики и упорядоченные записи `(PSP, merchant account, environment, версия конфигурации)` для данного Payment; не более одного account каждого PSP, секреты в снимок не входят. |

Root принимает решение, можно ли добавить Attempt; сама Entity инициализирует и хранит собственное состояние, включая время создания, полученное от вызывающего слоя. Домен не вызывает PSP, БД или часы напрямую. Один PSP не используется повторно новой попыткой в том же маршруте: техническая повторная доставка работы продолжает существующую Attempt.

## Денежные величины

| Величина | Источник | Использование |
|---|---|---|
| Цена покупки | Доверенный снимок владельца покупки | Не меняется при повторе команды и переключении PSP. |
| Основание котировки | Ответ PSP на сохранённые цену, валюту и условия создания | Проверяется до показа реквизитов; счёт на ошибочную цену не оплачивает исходную покупку. |
| Сумма к переводу | Котировка конкретной Attempt в выбранных активе и сети | Показывается покупателю вместе с реквизитами; не заменяется текущим курсом при проверке оплаты. |
| Фактически поступившая сумма | Подтверждённое наблюдение PSP | Сопоставляется с котировкой, активом, сетью и правилами допустимого отклонения. |
| Итоговая выплата merchant | Данные PSP после комиссий и конвертации | Не подменяет сумму, фактически внесённую покупателем. |

Деньги представляются точными десятичными значениями с правилами точности конкретного актива. Автоматическая замена актива или сети при переключении PSP изменила бы условия оплаты и не выполняется без нового решения покупателя.

## Наблюдения PSP и граница агрегата

Ответ создания, подписанный webhook и ответ аутентифицированного запроса статуса — разные источники сведений. Сырой ответ и его происхождение сохраняются до применения; адаптер формирует нормализованное наблюдение. Подпись подтверждает источник сообщения, но не достаточность суммы и не соответствие исходной покупке. Наблюдение — вход для агрегата, а не его дочерняя Entity.

Наблюдение содержит PSP, merchant account, среду, внешний ID, ссылку на Attempt, статус, денежные поля и времена события и получения. Неизвестная привязка или противоречие сохраняются для сверки. История входящих сообщений и аудит находятся вне коллекции дочерних Entity: их рост не должен увеличивать загружаемый агрегат. Payment получает только проверенные данные, необходимые для решения.

## Что проверяет Aggregate Root

1. Новая Attempt выбирается из сохранённого маршрута. Её PSP ещё не использовался в Payment, а порядковый номер не переиспользуется.
2. Добавление Attempt запрещено при неразрешённой предыдущей попытке или существующем счёте; доказанный no-create освобождает право рассмотреть следующего PSP.
3. Реквизиты и котировка закрепляются за той Attempt, которая создала счёт. Последующий статус `EXPIRED` или `FAILED` не стирает эту связь.
4. Принятое `PAID` не откатывается новым наблюдением; противоречие отмечается для отдельного разбора.

Уникальность Payment по покупке обеспечивается при сохранении и обработке повторной команды: один Aggregate Root не может проверить существование другого Payment.

Billing фиксирует факт оплаты и обязательство передать его модулю продукта; право доступа и уникальность его предоставления принадлежат модулю продукта. HTTP, проверка подписи, inbox, блокировки БД и транзакционная доставка находятся за границей агрегата. Условия переключения определены в [каскаде](../routing/cascade.md).

`CreatePaymentUseCase` создаёт агрегат; `StartPaymentAttemptUseCase` обращается к нему для новой попытки, `AdvancePaymentCascadeUseCase` — для безопасного продолжения, а `ApplyPaymentObservationUseCase` — для денежного решения. `GetPaymentStatusUseCase` читает сохранённый результат. Ответственность этих операций и ссылки на их последовательности находятся в [application](../contracts/application.md).
