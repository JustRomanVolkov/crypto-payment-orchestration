# Состояния Payment и Attempt

[Billing](../../README.md) → [Архитектура](../README.md) → [Агрегат Payment](payment.md)

Статус Payment описывает решение Billing по покупке. Статус Attempt описывает взаимодействие с одним PSP. Внешний статус провайдера переводится в наблюдение и не копируется напрямую в эти enum.

## Payment

| `PaymentStatusEnum` | Смысл |
|---|---|
| `PROCESSING` | Payment сохранён; счёт создаётся либо исход создания выясняется. |
| `AWAITING_PAYMENT` | Реквизиты одного созданного счёта сохранены и доступны покупателю. |
| `CONFIRMING` | Перевод обнаружен; окончательное денежное решение ещё не принято. |
| `PAID` | Достаточная оплата принята; результат покупки или обязательство передать факт оплаты модулю продукта сохранены атомарно. |
| `EXPIRED` | Срок существующего счёта истёк по данным PSP; поздние деньги ещё возможны. |
| `FAILED` | Безопасные варианты создания исчерпаны без принятой оплаты и без неразрешённого счёта. |
| `REQUIRES_REVIEW` | Автоматическое решение остановлено: требуется разбор исхода или денежного противоречия. |

Основные переходы: `PROCESSING → AWAITING_PAYMENT → CONFIRMING → PAID`. Проверенный окончательный факт может сразу перевести `PROCESSING` или `AWAITING_PAYMENT` в `PAID`, если промежуточные уведомления не пришли. `PROCESSING → FAILED` допустим после исчерпания безопасного маршрута; неизвестный исход ведёт к сверке и затем, при необходимости, к `REQUIRES_REVIEW`. После разбора Payment возвращается в ожидание, становится `PAID` либо завершается неуспехом в зависимости от доказанного исхода. Из `EXPIRED` или `FAILED` неожиданное поступление направляется на разбор, а не отбрасывается.

`PAID` не откатывается поздним или противоречивым сообщением. Для аномалии после принятой оплаты сохраняется отдельный `review_required` и причина, без смены исторического статуса. Состояние выдачи хранится отдельно от статуса Payment.

`FAILED` без созданного счёта не позволяет создать второй Payment для того же `purchase_id`: повтор того же намерения возвращает исходный Payment, новый ключ даёт конфликт. Если продукт разрешает повторную попытку покупки, он создаёт новое намерение и новый `purchase_id`. После `EXPIRED` с выданными реквизитами автоматическое предложение нового Payment опасно из-за возможного позднего перевода; сперва требуется сверка и решение по исходной покупке.

## Создание счёта у PSP

| Из Attempt | В Attempt | Основание |
|---|---|---|
| Новая | `PREPARED` | Сохранена попытка до начала отправки. |
| `PREPARED` | `CREATING` | Маркер начала create сохранён до сетевого вызова. |
| `PREPARED` | `CREATE_REJECTED` | Доказано, что отправка не начиналась. |
| `CREATING` | `AWAITING_PAYMENT` / `INVOICE_UNVERIFIED` | Счёт создан; реквизиты проверены либо требуют уточнения. |
| `CREATING` | `CREATE_REJECTED` / `CREATE_UNKNOWN` | Доказано отсутствие счёта либо исход ещё не установлен. |
| `CREATE_UNKNOWN` | `AWAITING_PAYMENT` / `INVOICE_UNVERIFIED` | Счёт найден; реквизиты проверены либо требуют уточнения. |
| `CREATE_UNKNOWN` | `CREATE_REJECTED` / `REQUIRES_REVIEW` | Получено доказательство no-create либо автоматическая сверка не установила исход. |
| `INVOICE_UNVERIFIED` | `AWAITING_PAYMENT` / `REQUIRES_REVIEW` | Котировка и реквизиты проверены либо подтвердить их не удалось. |

`PREPARED` — сохранённая Attempt без начатой отправки. Переход в `CREATING` фиксируется до сетевого вызова; после него падение worker оставляет возможность выполненного `POST`, даже если ответ не записан. Истёкший lease не отменяет внешний запрос. `CREATE_REJECTED` означает доказанное отсутствие созданного счёта и его позднего появления; timeout или пустой поиск таким доказательством не являются.

Из `CREATE_UNKNOWN` разрешён переход к `CREATE_REJECTED` только при подтверждённом контрактом PSP доказательстве no-create, исключающем позднее исполнение. Для [NOWPayments](../providers/nowpayments.md) такой автоматический переход не подтверждён. Состояние `REQUIRES_REVIEW` не превращает неопределённость в отказ.

Если проверенный финальный факт пришёл раньше ответа создания, Attempt может перейти из `CREATING` или `CREATE_UNKNOWN` сразу в `SETTLED` после сопоставления счёта, котировки и перевода. При недостающих полях наблюдение ожидает сверки.

## После создания счёта

| `PaymentAttemptStatusEnum` | Смысл |
|---|---|
| `INVOICE_UNVERIFIED` | Существование счёта и его ID подтверждены, но реквизиты или котировку ещё нельзя проверить; Payment остаётся `PROCESSING`, покупателю не предлагается перевод. |
| `AWAITING_PAYMENT` | Счёт и реквизиты сохранены. |
| `PARTIALLY_PAID` | Есть поступление ниже принятого порога; доплата или разбор по правилам продукта. |
| `CONFIRMING` | Перевод обнаружен, но окончательные условия ещё не выполнены. |
| `SETTLED` | Получен финальный факт по контракту PSP; Payment станет `PAID` только после проверки суммы, актива, сети и привязки. |
| `EXPIRED` / `FAILED` | Существующий счёт истёк или его оплата не завершилась; это не `CREATE_REJECTED` и не разрешение переключить PSP. |
| `REQUIRES_REVIEW` | Поступление или сведения PSP противоречивы; нужна сверка или решение оператора. |

Поздний webhook не определяет время перевода: для решения учитывается подтверждённое время поступления. Новые денежные наблюдения сохраняются и после конечного статуса Attempt. Право на следующего PSP описывает [каскад](../routing/cascade.md), а не числовой порядок enum.
