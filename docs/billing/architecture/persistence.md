# PostgreSQL: хранение Billing

[Billing](../README.md) → [Архитектура](README.md) → Хранение

Billing владеет своими таблицами в схеме `billing` общей или отдельной PostgreSQL БД. Их состав и ограничения не зависят от размещения приложения. Таблица однократной выдачи принадлежит модулю продукта. [Доменный агрегат](domain/payment.md) не загружает историю всех сообщений PSP.

## Таблицы Billing

| Таблица | Основные данные | Назначение |
|---|---|---|
| `billing.payments` | ID, tenant/owner и purchase ID, ключ и fingerprint первоначального намерения; снимок покупки и маршрута; статус, срок новых create, `next_action_at`, версия/claim | Одна логическая оплата и долговременное продолжение работы, в том числе подготовленной или незавершённой Attempt. |
| `billing.payment_attempts` | Payment FK, номер маршрута, PSP/account/environment, merchant reference и внешний ID; исход создания, сохранённый запрос, котировка, реквизиты и статус | Одна попытка у конкретного PSP; число строк на Payment не ограничено константой. |
| `billing.provider_observations` | Источник и namespace, внешний event ID при надёжной семантике, hash и исходное свидетельство, нормализованные поля, nullable привязка к Payment/Attempt, состояние применения и срок проверки | Webhook, ответ create и authenticated GET сохраняются до принятия денежного решения; неизвестная привязка допускается. |
| `billing.payment_audit` | Время, автор/источник, причина, ссылки на Payment, Attempt и observation при их наличии, старое и новое решение | Добавляемая история решений и ручного разбора; не бухгалтерский ledger. |

Снимок маршрута хранится упорядоченным значением с версией политики и записями PSP/account/environment/config version; схема не добавляет колонку на каждый PSP. Секреты и ключи API находятся вне Payment. Для наблюдения исходные данные и их hash неизменяемы; привязка и состояние обработки могут дополняться без переписывания свидетельства.

При [раздельных транзакциях](flows/payment-to-product.md#раздельные-sql-транзакции) добавляется `billing.outbox_events` для обязательства доставить факт оплаты модулю продукта. Входящий inbox и grant находятся у получателя. Общий commit выдачи не требует outbox именно для этой границы; долговременная фоновая работа самого Billing сохраняется в любом варианте.

## Ограничения и индексы

| Ограничение | Что защищает |
|---|---|
| `UNIQUE(tenant_id, purchase_id)` в `payments` | Второй ключ не создаёт другой Payment той же покупки. |
| `UNIQUE(tenant_id, operation, idempotency_key)` и сохранённый `request_fingerprint` | Повтор сначала находит прежний Payment; совпадение намерения проверяется приложением, конфликт возвращает ошибку. |
| FK Attempt → Payment; `UNIQUE(payment_id, ordinal)`, `UNIQUE(payment_id, provider)` | Номер не переиспользуется, тот же PSP не получает новую Attempt в одном Payment. Принадлежность записи снимку маршрута проверяет агрегат. |
| `UNIQUE(provider, merchant_account, environment, merchant_reference)` | Ссылка на Attempt не относится к двум исходным запросам. |
| Уникальный частичный индекс на `(provider, merchant_account, environment, external_id)` при `external_id IS NOT NULL` | Известный внешний счёт не привязывается к двум Attempts; неизвестный ID остаётся допустимым. |
| Дедупликация точного наблюдения по namespace, source и hash; поиск по надёжному event ID без запрета другого hash | Точный дубль не создаёт новый факт; противоречивые версии одного события сохраняются для разбора. |

Уникальность однократной выдачи по `(tenant_id, purchase_id)` обеспечивает модуль продукта **в своей** таблице. Дополнительное поступление не блокируется ограничением «только один внешний счёт»: его свидетельство должно сохраниться. Проверка достаточности суммы и допустимых переходов остаётся в домене, а не заменяется набором SQL `CHECK`.

Цена и криптовалютные суммы хранятся как точные `NUMERIC` с валютой/активом/сетью. Для начального набора активов достаточно `NUMERIC(38,18)`; актив с большей точностью допускается только после расширения схемы. Приложение проверяет точность до сохранения: тихое округление запрещено. Время хранится как `timestamptz`. Индексы покрывают наступивший `next_action_at`, ожидающие применения observations, внешние ID и историю Payment. Ограниченный размер и доступ к raw payload нужны независимо от его формата.

PostgreSQL поддерживает [частичные уникальные индексы](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS) и [`SKIP LOCKED` для конкурентного выбора работы](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE). Как именно выполняются claim, commit и восстановление, описано в [обработке](processing.md).
