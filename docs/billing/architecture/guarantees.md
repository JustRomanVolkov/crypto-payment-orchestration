# Гарантии Billing

[Billing](../README.md) → [Архитектура](README.md) → Гарантии

Гарантии относятся к одной логической оплате покупки независимо от числа PSP и способа развёртывания Billing. При неоднозначном ответе внешней системы безопасность денежного решения имеет приоритет над немедленным продолжением checkout.

## Инварианты

| Область | Обязательное поведение |
|---|---|
| Повтор команды | Повтор с тем же ключом и тем же намерением возвращает сохранённый Payment. Конфликтующее намерение с тем же ключом отклоняется. |
| Маршрут | Payment сохраняет применённый порядок допущенных PSP. Изменение конфигурации не переставляет уже начатый маршрут; PSP с отозванным допуском не получает новых запросов. |
| Переключение | Следующий PSP допустим только до отправки запроса предыдущему либо после доказанного отсутствия счёта и возможности его позднего создания. Timeout, `5xx`, отсутствие webhook и истечение lease сами по себе этого не доказывают. |
| Существующий счёт | Выданные реквизиты остаются привязанными к своей попытке и PSP. Новые запросы можно остановить, но проверку поступлений по старому счёту прекращать нельзя. |
| Денежный результат | `PAID` фиксируется только после проверки принадлежности платежа, статуса, актива, сети и достаточности фактически поступившей суммы по сохранённым условиям покупки. |
| Предоставление покупки | Подтверждённая оплата и локальный результат покупки либо обязательство передать факт оплаты модулю продукта сохраняются атомарно. Модуль продукта обеспечивает один результат по идентификатору покупки, даже если уведомление повторится. |
| Поздние факты | Новое наблюдение о переводе сохраняется и разбирается даже после завершения Payment; повторная выдача из него не следует. |
| Восстановление | Неоконченная работа остаётся в долговременном состоянии и может быть продолжена после восстановления зависимостей. Потеря сообщения очереди не означает потери платёжного обязательства. |

Детальные состояния, ключи и транзакционные механизмы описаны в профильных документах [архитектуры](README.md) и [вариантов размещения](../roadmap/README.md); здесь закреплены свойства, которым они должны соответствовать.

## Пределы

- Billing не может запретить покупателю отправить криптовалюту дважды или отменить уже совершённый перевод. Дополнительное поступление должно быть обнаружено и передано на разбор.
- Неизвестный результат создания счёта может потребовать ручной сверки с PSP. Отсутствие записи в доступном поиске не всегда исключает позднее исполнение запроса.
- Продвижение платежа зависит от доступности PostgreSQL, исполнителей и данных PSP. Целевые сроки восстановления и сохранность после катастрофической потери БД задаются отдельно; наличие резервной копии само по себе не гарантирует нулевую потерю данных.

При восстановлении после потери подтверждённого состояния новые счета не создаются до сверки с PSP: внешний перевод мог состояться после последней сохранённой точки.
