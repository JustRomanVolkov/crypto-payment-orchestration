# Идемпотентность и конкуренция

[Billing](../README.md) → [Архитектура](README.md)

Повтор клиента, задача worker, ответ PSP и webhook пересекают разные границы. Одного ключа для них нет: каждый повтор должен сохранять свой бизнес-эффект. Гарантии сформулированы в [общем разделе](guarantees.md); здесь указаны механизмы.

## Ключи и эффект

| Граница | Ключ и проверка | Что не повторяется |
|---|---|---|
| Команда клиента | `(tenant_id, операция, idempotency_key)` и отпечаток первоначального намерения | Повтор возвращает тот же Payment; другой запрос с тем же ключом даёт конфликт. |
| Покупка | `UNIQUE(tenant_id, purchase_id)` | Новый ключ не создаёт вторую логическую оплату той же покупки. |
| Attempt | ID, уникальный PSP внутри Payment и условный переход `PREPARED → CREATING` | Два worker не получают право одновременно инициировать один create. |
| Внешний счёт | `(PSP, merchant account, environment, external_id)` | Один внешний объект не привязывается к разным Payment. |
| Уведомление PSP | Документированный event ID в его пространстве имён и hash payload; при отсутствии ID — fingerprint проверенного сообщения | Точный дубль не применяется дважды; изменённое сообщение сохраняется отдельно. |
| Наблюдение | Собственный ID и состояние применения | Падение после сохранения позволяет повторить применение того же факта. |
| Предоставление покупки | Уникальность результата по `(tenant_id, purchase_id)` в модуле продукта | Повторы оплаты или доставки не дают второй продукт. |

Отпечаток команды описывает поля исходного запроса клиента, а не текущую цену каталога. Поэтому повторный запрос сначала ищет прежний Payment и возвращает его сохранённые условия; новую цену читает только новая команда. При гонке вставок проигравшая транзакция откатывается, затем читает победившую запись и проверяет владельца и отпечаток. Уникальность покупки — ограничение хранилища, не метод одного Aggregate Root.

## Повторы внешних сообщений

Event ID используется для дедупликации только при подтверждённой семантике PSP. Тот же ID с другим содержимым не перезаписывает старый факт: оба payload сохраняются с признаком конфликта для сверки. Если ID нет, hash полного проверенного сообщения подавляет точный дубль, но не заменяет бизнес-проверку. Два ответа GET с одинаковым статусом и разными суммами остаются разными наблюдениями.

Webhook получает подтверждение после долговременного сохранения. Применение наблюдения выполняется отдельной транзакцией под защитой Payment; её rollback оставляет факт ожидающим повторного применения. `PAID` и локальная выдача либо обязательство доставки фиксируются вместе. После разделения транзакций получатель защищает собственную выдачу уникальным ключом и входящим inbox.

## Гонки вокруг создания счёта

| Ситуация | Правило |
|---|---|
| Два исполнителя видят `PREPARED` | Только победитель сохранённого условного перехода в `CREATING` может отправить запрос PSP. |
| Процесс падает после `CREATING` | Новый worker не повторяет `POST`: вызов мог состояться. Исход выясняется по [сверке](flows/reconciliation.md). |
| Старый исполнитель пережил lease | Его внешний запрос всё ещё может завершиться; истечение lease не доказывает no-create и не разрешает fallback. |
| Webhook и GET одновременно подтверждают оплату | Оба факта сохраняются; блокировка Payment и уникальность выдачи ограничивают бизнес-эффект одним результатом. |
| Worker упал после commit, до ACK | Повтор читает уже сохранённый результат и завершает работу без повторной выдачи или PSP create. |

Внешний HTTP не выполняется внутри транзакции БД. Повтор SQL-операции после конфликта не включает автоматический повтор `POST` к PSP. `order_id` или другой merchant reference помогает найти Attempt, но не является внешним ключом идемпотентности без явной гарантии провайдера. Между БД, очередью и PSP нет общей транзакции: однократность достигается для **бизнес-эффекта**, а не для доставки сообщений.
