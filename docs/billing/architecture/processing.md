# Транзакции и фоновая обработка

[Billing](../README.md) → [Архитектура](README.md) → Фоновая обработка

PostgreSQL хранит состояние, свидетельства PSP и срок следующего действия. Taskiq передаёт worker ID работы через Redis Streams. Создание счёта и применение наблюдений выполняются этими фоновыми операциями при любом варианте размещения. Очередь может доставить ID повторно или временно не доставить его; завершённость определяется данными PostgreSQL. [Правила каскада](routing/cascade.md) и [идемпотентности](consistency.md) не меняются от способа доставки.

## Границы транзакций

| Действие | Что фиксируется одной локальной транзакцией | После commit |
|---|---|---|
| Создать Payment | Снимок покупки и маршрута, `PROCESSING`, ключ повтора и срок первой работы; без Attempt. | Вернуть ID и отправить необязательный сигнал Taskiq. |
| Зарезервировать Attempt | Под блокировкой Payment проверить следующий допустимый PSP, создать `PREPARED` с постоянным reference и сроком продолжения. | Подготовить единоличный dispatch. |
| Начать create | Условно перевести `PREPARED → CREATING`, сохранить на Payment срок выяснения исхода. | Один `POST` к PSP без открытой SQL-транзакции. |
| Принять наблюдение | Проверенное свидетельство и `PENDING` с возможностью повторного применения. | После commit ответить `2xx` на webhook; сигнал на обработку необязателен. |
| Применить наблюдение | Под блокировкой Payment проверить факт, обновить Attempt/Payment, audit, отметку наблюдения и следующую работу. При `PAID` сохранить локальный grant либо outbox в зависимости от выбранной границы. | Подтвердить сигнал Taskiq после commit; при ошибке повторить SQL-операцию по сохранённому состоянию. |

Условия общего commit и rollback выдачи описаны в [общей транзакции](flows/payment-to-product.md#общая-sql-транзакция); работа relay и подтверждение получателя — в [доставке оплаты](flows/payment-to-product.md#раздельные-sql-транзакции). Вызов PSP и любая удалённая выдача находятся за пределами транзакции. Для локальных изменений используется `READ COMMITTED`, блокировка нужного Payment и ограничения БД; при конфликте SQL-часть перечитывает состояние. Повтор SQL-части не повторяет внешний `POST`.

## Доставка и восстановление

`RedisStreamBroker` выбран для Taskiq, поскольку [поддерживает подтверждение сообщений](https://github.com/taskiq-python/taskiq-redis#stream); задачи содержат ID, а не единственную копию платёжных данных. Worker перед внешним действием проверяет текущее SQL-состояние и получает право работы коротким claim. Повторная доставка или истёкший lease не разрешают отправить ещё один `POST` из `CREATING`.

Отдельный SQL scanner при запуске и периодически находит ограниченные порции просроченной работы: Payment с `next_action_at`, ожидающие observations, попытки с невыясненным create и, при наличии, неподтверждённые outbox-события. Он публикует ID в Taskiq и сам не вызывает PSP. Публикация не завершает SQL-обязательство; ограничение повторных сигналов не должно удалять исходный срок работы. Если Redis недоступен, после восстановления ID публикуется снова. Выбор нескольких исполнителей можно распределять через [`FOR UPDATE SKIP LOCKED`](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE); он подходит для очередеподобной выборки, но не заменяет согласованное чтение Payment.

| После сбоя видно в PostgreSQL | Продолжение |
|---|---|
| Payment без Attempt, срок наступил | Заново проверить текущий допуск и зарезервировать первую пригодную запись маршрута. |
| `PREPARED` без `CREATING` | Победитель условного перехода фиксирует `CREATING` до сети; проигравший ничего не отправляет. |
| `CREATING` без ответа, срок выяснения наступил | Считать исход неизвестным и [сверять](flows/reconciliation.md), без повторного create и fallback. |
| `CREATE_REJECTED` с безопасным правом продолжить | По сохранённому `next_action_at` рассмотреть следующего PSP, пока открыт срок новых create. |
| `PENDING` observation | Повторно применить сохранённый факт; если его привязка неизвестна, назначить корреляцию или разбор. |
| Результат уже закоммичен, Taskiq доставил ID ещё раз | Прочитать состояние и завершить задачу без нового внешнего эффекта. |

Временный сбой GET назначает следующий срок с ограниченным backoff и квотой account; лимит автоматической сверки приводит к разбору, а не к доказанному no-create. Поздний ответ старого worker всегда сначала сохраняется как свидетельство. Lease и token ограничивают право менять расписание, но не отменяют потенциально отправленный запрос PSP. Фактическое поведение redelivery/ACK проверяется на закреплённых версиях Taskiq и Redis; подтверждение сообщения не заменяет SQL-инварианты.

Период scanner, размер batch, предел параллелизма и бюджет запросов на PSP/account выбираются по [возрасту работы и измеренной скорости обработки](../operations/capacity.md). Для уже полученных денежных фактов, сверки и доставки выдачи оставляется отдельный бюджет исполнения: поток новых create не должен вытеснять их.
