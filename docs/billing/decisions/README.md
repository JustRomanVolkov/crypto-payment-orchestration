# Решения по реализации Billing

[Billing](../README.md) → Решения

Здесь собраны основания для исходной реализации. [Архитектура](../architecture/README.md) задаёт правила Payment и PSP, [развитие](../roadmap/README.md) — допустимые варианты размещения, [альтернативы](alternatives.md) — цену других решений и условия пересмотра. Неизвестный исход create, проверка фактических денег и однократное предоставление покупки остаются обязательными при любом выборе.

| Вопрос | Исходное решение | Основание |
|---|---|---|
| Размещение | [Модульный монолит с общей БД](../roadmap/modular-monolith-shared-db.md). | Используем существующие приложение и PostgreSQL; отдельную БД или приложение можно выбрать сразу при требовании иной границы. |
| Несколько PSP | [Адаптеры в Billing](../architecture/contracts/provider-adapter.md) и сохранённый маршрут с [фиксированным приоритетом](../architecture/routing/policy.md). | Начальная задача — проверяемое переключение после доказанного no-create, а не оптимизация распределения трафика. |
| Фоновая работа | [PostgreSQL хранит обязанности](../architecture/processing.md); Taskiq/Redis Streams передают ID задачи. | Потерянный сигнал не удаляет Payment, наблюдение или срок следующего действия. Создание счёта и применение наблюдений фоновые с первого дня. |
| Оплата и покупка | [Один commit](../architecture/flows/payment-to-product.md#общая-sql-транзакция), если модуль продукта может использовать ту же БД и UoW; иначе [outbox/inbox](../architecture/flows/payment-to-product.md#раздельные-sql-транзакции). | Выбор зависит от реальной SQL-границы, а не от того, работают ли фоновые задачи. |

Перед включением PSP нужны допуск конкретной adult AI-платформы, условия merchant account и проверенный контракт create/webhook/GET. Для общих транзакций требуется подтвердить локальную операцию продукта с общей UoW. Пропускная способность и бюджеты задержек пока [расчётные](../operations/capacity.md) и уточняются по бизнес-прогнозу и испытаниям.
