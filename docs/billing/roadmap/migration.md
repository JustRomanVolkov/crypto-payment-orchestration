# Переход между вариантами архитектуры

[Billing](../README.md) → [Развитие](README.md) → Миграция

Каждое изменение решает отдельное требование. Для новой системы выбирается подходящий исходный вариант без миграции; для существующей сохраняются Payment, маршрут, идентификаторы Attempt, наблюдения, ключи повторов и незавершённые обязанности. Перенос не превращает неизвестный create в безопасный отказ.

## Зависимости изменений

| Изменение | Что должно быть готово до переключения |
|---|---|
| Общий commit → раздельные commit в той же БД | Идемпотентный получатель, уникальность grant, outbox и повторяемая доставка. |
| Общая БД → отдельная БД Billing | Раздельные commit уже проверены; покупка передаётся снимком, межмодульные SQL/FK устранены. |
| Монолит → микросервис с той же БД Billing | Изолированный доступ к данным, совместимые сетевые адаптеры, приём старых callback и эксплуатационная ответственность. |

Из общей БД можно перейти сразу к микросервису в одном согласованном переключении, если выполнены обе последние группы требований. Промежуточный производственный запуск монолита с отдельной БД не обязателен. Масштабирование API/workers может происходить независимо от всех строк.

## Общий commit → доставка оплаты

1. Закрепить единую уникальность grant по покупке и проверку совпадения параметров для старой локальной операции и нового получателя.
2. Подготовить outbox, relay и inbox; проверить повторы и падение после commit получателя до подтверждения Billing.
3. На переключении остановить и завершить исполнителей применения наблюдений старой версии. Для ещё не принятой оплаты включить один путь: `PAID + outbox`. Приём и сохранение webhook может продолжаться отдельно.
4. Для уже `PAID` с локальным grant не создавать обязательство повторно. Ранее начатую доставку, если она есть, довести до подтверждения; расхождения разбирать по Payment, observation и grant.

Откат версии не должен включать локальную выдачу поверх незавершённой доставки без проверки того же ключа покупки. Смена способа согласованности не отменяет уже зафиксированный результат продукта.

## Перенос БД с согласованной паузой записи

Исходный способ миграции предполагает согласованное окно недоступности записи; его длительность определяется пробным переносом. Непрерывная миграция без такой паузы требует отдельного протокола репликации и переключения, здесь она не обещается.

1. Подготовить целевую БД с теми же ограничениями, индексами и правами. Проверить перенос и обратную совместимость приложения на копии; выбрать окно и ответственных за сверку.
2. Остановить приём новых команд записи, scanner, relay и все workers, меняющие Billing. Завершить выполняющиеся SQL-транзакции; исключить новые исходящие вызовы старых процессов. Уже отправленный PSP create всё равно мог выполниться: его неопределённость переносится вместе с Attempt.
3. На время окончательного снимка и переключения webhook получает `5xx`, если его нельзя сохранить в действующем источнике записи. Нельзя вернуть `2xx` за приём в память или в старую БД после снимка. До окна подтвердить повторную доставку PSP либо иной проверенный способ восстановить пропущенные факты.
4. Перенести согласованный набор таблиц Billing: Payment, Attempt, observations, audit, outbox, расписание и ключи идемпотентности. Сверить содержимое и ограничения; старая БД остаётся без записывающих клиентов.
5. Переключить API, webhook, workers и scanner на новый источник, затем восстановить приём. Проверить повтор команды, найденные/неопределённые create, применение наблюдений и незавершённую выдачу. Повторы webhook и разрешённая сверка восполняют окно недоступности.

Паузы только новых create недостаточно: наблюдения, результаты workers и подтверждения relay тоже меняют состояние. Простая двойная запись в две БД не используется. До первой записи в новую БД возврат на старую возможен после проверки; после новых записей и внешних эффектов возврат требует обратной синхронизации и сверки, а не смены connection string.

## Выделение приложения без повторного переноса данных

Когда БД Billing уже изолирована, переносить её ради нового деплоя не нужно. Подготавливаются сетевые адаптеры покупки и выдачи, права процесса, секреты и маршруты API. Старые исполнители отключаются от записи/dispatch до передачи ответственности новому приложению; незавершённые состояния продолжаются из той же БД.

Ранее заданные PSP callback URL сохраняют рабочую маршрутизацию к действующему приёмнику. Прокси возвращает успех только после подтверждённого сохранения наблюдения. Совместимость API и событий проверяется для смешанных версий сторон; тайм-аут доставки не порождает новый event ID. Условия изоляции зависимостей заданы в [варианте микросервиса](billing-microservice.md).
