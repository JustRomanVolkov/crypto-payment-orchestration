# Восстановление Billing после сбоя

[Billing](../README.md) → Эксплуатация → Восстановление

При инциденте сначала устанавливают, какие Payment и merchant accounts затронуты и какие действия уже могли произойти у PSP. Основание для продолжения — сохранённые Payment, Attempt, наблюдения, сроки работы и, если используется, outbox. Потеря ответа PSP или сигнала Taskiq не доказывает, что действие не состоялось. [Правила перехода к другому PSP](../architecture/routing/cascade.md) действуют и при восстановлении.

## Действия по виду сбоя

| Сбой | Что проверить и как продолжить |
|---|---|
| Redis или workers недоступны | После восстановления запустить SQL scanner и исполнителей; сопоставить готовые Payment, ожидающие наблюдения и outbox с выполненной работой. Из `CREATING` нельзя повторно отправлять `POST` по одному лишь истечению времени или lease. |
| Ответ на create потерян | Сохранить исходный reference, PSP/account и Attempt; выполнить допустимую [сверку](../architecture/flows/reconciliation.md). Если отсутствие счёта и позднего исполнения не доказано, оставить исход неопределённым и назначить разбор, не переходя к следующему PSP. |
| Webhook не удалось сохранить | Вернуть PSP `5xx`; после восстановления проверить повторную доставку и доступные факты PSP. Если контракт PSP не гарантирует повтор, искать пропущенные сведения разрешённым GET, отчётом или через поддержку; успешный ответ за несохранённое сообщение не выдаётся. |
| Модуль продукта недоступен | При общем commit сохранённое ранее наблюдение остаётся для повторного применения; `PAID` с grant не фиксируются по отдельности. При раздельных транзакциях уже сохранённые `PAID` и outbox остаются; после восстановления доставить тот же event ID и проверить inbox/grant, прежде чем подтвердить доставку. |
| PostgreSQL восстановлена из резервной копии | Приостановить новые create и запись до сверки восстановленных Payment, Attempt, наблюдений и результатов продукта с внешними счетами и переводами PSP за утраченное окно. Уже отправленный `POST` мог создать счёт без сохранившейся записи; неизвестный исход не разрешает новый счёт. Webhook без долговременного сохранения получает `5xx`. |

## Возобновление работы

Для каждого затронутого Payment сопоставляют исходную покупку, сохранённый маршрут, Attempt/reference, счета и денежные факты PSP, исходные наблюдения Billing и уже предоставленный результат покупки. Отдельные БД восстанавливают с учётом отсутствия общего момента commit: расхождение outbox и inbox/grant требует сверки по стабильным идентификаторам. Нельзя считать сохранённый `PAID` основанием повторно предоставить покупку без проверки её ключа уникальности.

После сверки возвращают приём записей и фоновую обработку, контролируя возраст готовой работы и [задержку предоставления покупки](metrics.md). Неустановленный исход create, непривязанный перевод или противоречивые факты остаются в назначенном [разборе](../architecture/flows/exceptions.md) с ответственным и сроком следующего действия; они не становятся доказанным отказом из-за завершения инцидента. [Проверки этих случаев](verification.md) задают ожидаемые результаты испытаний.
