# Проверка гарантий Billing

[Billing](../README.md) → Эксплуатация → Проверки

Проверки воспроизводят отказы на управляемом PSP-адаптере и реальных транзакциях тестовой PostgreSQL. Сетевые ответы PSP, повторные webhook и падения worker задаются явно; результаты сравниваются с [инвариантами Billing](../architecture/guarantees.md). Контракты и квоты конкретного PSP проверяются отдельно: успешный тест адаптера не доказывает его внешних гарантий.

| Сценарий испытания | Проверяемый результат |
|---|---|
| Повторить команду с тем же ключом, затем изменить намерение и отдельно повторить покупку с новым ключом | Исходный Payment возвращается для того же намерения; конфликт не создаёт вторую оплату покупки. |
| Запустить конкурирующие workers для одной Attempt, оборвать процесс до/после `CREATING` и после отправки `POST` | Только исполнитель подтверждённого перехода может отправить исходный запрос. После возможной отправки повтор задачи не отправляет новый `POST`. |
| Вернуть timeout или `5xx` на create; отдельно подтвердить окончательное no-create | Неизвестный исход удерживает каскад. Новая Attempt у следующего PSP появляется только при доказанной безопасности и открытом сроке новых create. |
| Создать счёт, затем прислать поздний webhook, дубль и противоречащие денежные поля | Все различные свидетельства сохраняются; точный дубль не повторяет эффект. Существующий счёт и поздний перевод не разрешают автоматический fallback. |
| После `EXPIRED` разрешить новую покупку по решению модуля продукта, затем обнаружить оплату старого счёта | Новое намерение связано с исходным. Поступление по старому счёту сохраняется и направляется на разбор без автоматической выдачи по исходной покупке; при разборе учитывается, предоставлен ли результат по новому намерению. |
| Отправить webhook с неверной подписью и отдельно вызвать сбой сохранения подлинного сообщения | Неверный источник отклоняется; за подлинный, но несохранённый факт Billing не отвечает `2xx`. |
| Передать неверные сумму, актив, сеть или недостаточную финальность, затем достаточное подтверждение | До полной проверки `PAID` и предоставления покупки нет. Достаточный факт даёт один результат по ключу покупки. |
| Убить worker после commit наблюдения, до его применения | Сохранённое наблюдение находится сканером и применяется после восстановления. |
| Убить worker до и после общего commit оплаты и результата покупки | До commit `PAID` и grant откатываются вместе; после commit повтор не создаёт второй grant. Исходное наблюдение остаётся пригодным для повторного применения. |
| При раздельных транзакциях потерять ответ получателя после его commit и остановить relay | `PAID` и outbox сохраняются; повтор того же event ID не создаёт второй grant, а подтверждение доставки записывается после результата получателя. |
| Потерять сигнал Redis при сохранённом сроке работы | Scanner повторно обнаруживает готовую работу; её исполнение не создаёт второй счёт и не теряет наблюдение. |
| Восстановить БД из снимка, сделанного до возможного ответа PSP | Новые create по затронутым Payment остаются остановленными до [сверки с PSP](recovery.md); потерянный локальный ответ не считается no-create. |

Для каждой проверки фиксируют состояние Payment/Attempt, сохранённые observations и audit, число отправленных create, результат покупки и незавершённую работу. [Расчётные профили нагрузки и задержек](capacity.md) проверяются отдельно от корректности переходов; требования бизнеса и реальные квоты PSP ещё не подтверждены.
